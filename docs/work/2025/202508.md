"@xmly/xm-utils": "~3.0.0"  // 仅允许补丁更新（>=3.0.0 <3.1.0）

```json
"@xmly/xm-utils": "3.0.0"  // 完全禁止自动更新
```

### npm 和 yarn 的“原罪”：那个又大又慢的 node_modules

在聊 pnpm 的好处之前，我们得先搞明白，npm 和 yarn（特指 yarn v1）到底有什么问题。
它们最大的问题，都源于一个东西——扁平化的 node_modules。
你可能觉得奇怪，“扁平化”不是为了解决 npm v2 时代的“依赖地狱”问题吗？是的，它解决了老问题，但又带来了新问题：

1. “幽灵依赖”（Phantom Dependencies）
   这是我最不能忍受的一个问题。
   举个例子：你的项目只安装了 A 包（npm install A）。但是 A 包自己依赖了 B 包。因为是扁平化结构，B 包也会被提升到 node_modules 的根目录。
   结果就是，你在你的代码里，明明没有在 package.json 里声明过 B，但你却可以 import B from 'B'，而且代码还能正常运行！
   这就是“幽灵依赖”。它像一个幽灵，让你的项目依赖关系变得混乱不堪。万一有一天，A 包升级了，不再依赖 B 了，你的项目就会在某个意想不到的地方突然崩溃，而你甚至都不知道 B 是从哪来的。

2.磁盘空间的巨大浪费

3.安装速度的瓶颈
虽然 npm 和 yarn 都有缓存机制，但在安装依赖时，它们仍然需要做大量的 I/O 操作，去复制、移动那些文件。

pnpm 是怎么解决这些问题的？——“符号链接”
好了，现在主角 pnpm 登场。pnpm 的全称是“performant npm”，意为“高性能的 npm”。它解决上面所有问题的核心武器，就两个字：链接。pnpm 没有采用扁平化的 node_modules 结构，而是创建了一个**嵌套的、有严格依赖关系**的结构。

1. 彻底告别“幽灵依赖”
   在 pnpm 的 node_modules 里，你只会看到你在 package.json 里明确声明的那些依赖。
   你项目里依赖的 A 包，它自己所依赖的 B 包，会被存放在**node_modules/.pnpm/**这个特殊的目录里，然后通过 **符号链接**（Symbolic Link） 的方式，链接到 A 包的 node_modules 里。
   这意味着，在你的项目代码里，你根本访问不到 B 包。你想 import B？对不起，直接报错。这就从结构上保证了，你的项目依赖关系是绝对可靠和纯净的。
2. 磁盘空间的“终极节约”
   pnpm 会在你的电脑上创建一个“全局内容可寻址存储区”（content-addressable store），通常在用户主目录下的.pnpm-store 里。
   你电脑上所有项目的所有依赖，都只会在这个全局仓库里，实实在在地只存一份。
   当你的项目需要 lodash 时，pnpm 不会去复制一份 lodash 到你的 node_modules 里，而是通过 硬链接（Hard Link） 的方式，从全局仓库链接一份过来。硬链接几乎不占用磁盘空间。
   这意味着，就算你有 100 个项目都用了 lodash，它在你的硬盘上也只占一份的空间。这个特性，对于磁盘空间紧张的同学来说，简直是福音。

## 软连接(符号连接)和硬连接区别

### 硬链接（Hard Link）​​

硬链接是 ​​ 指向同一磁盘数据块 ​​ 的多个文件名，所有硬链接共享相同的文件内容（inode）。删除任一硬链接不影响数据，仅当所有硬链接被删除后文件才被释放。

### 硬连接 pnpm 中的作用 ​​

​- ​ 全局共享依赖存储

- ​​ 节省磁盘空间与安装时间

### 符号链接（软链接）

是一个指向目标文件或目录的 ​​ 路径指针 ​​，类似于操作系统的“快捷方式”。当访问软链接时，系统会跳转到其指向的实际路径

### 软连接在 pnpm 中的作用 ​​

​- ​ 构建依赖树结构 ​​
在项目的 node_modules 目录中，每个直接依赖（如 vue）以 ​​ 软链接形式存在 ​​，指向 .pnpm 目录下的真实包文件。

- 解决依赖嵌套问题
- 避免“幽灵依赖”

### 两者总结

​​- 硬链接解决存储与效率问题 ​​
全局 Store 硬链接确保包内容唯一性，避免重复。
​​- 符号链接解决依赖解析问题 ​​
软链接模拟嵌套结构，兼容 Node.js 模块查找逻辑，同时隔离依赖版本（如 A 用 B@1.0，C 用 B@2.0）。
​​- 根治传统包管理器缺陷 ​​
​​ 幽灵依赖 ​​：仅声明依赖可见（软链接控制）。
​​ 依赖分身 ​​：硬链接确保相同版本唯一存储。
​​ 嵌套过深 ​​：扁平化 .pnpm 结构避免路径过长。

- MD5 (Message-Digest Algorithm 5)是一种广泛使用的哈希函数,主要用于生成数据的**唯一标识**（哈希值）。其核心特点是 ​**​ 不可逆**​​（无法从哈希值反推原始数据）和 ​**​ 抗碰撞性**​​（不同数据产生相同哈希值的概率极低）。在前端开发中，MD5 常用于以下场景：

::: info

1. ​​ 文件完整性校验 ​

```js
原理​​：计算文件的MD5哈希值，与服务器提供的哈希值比对，确保文件传输无损坏或篡改。
示例​​：
// 计算文件MD5
const fileHash = await getFileMD5(file);
// 与服务器返回的哈希比对
if (fileHash !== serverHash) throw new Error('文件损坏');
```

2.文件/数据去重 ​

```js
​​原理​​：相同数据的MD5值必然相同，因此可快速判断重复内容。

∙​示例​​：
const imageHashes = new Set();
function checkDuplicate(file) {
  const hash = getFileMD5(file);
  if (imageHashes.has(hash)) return true; // 重复文件
  imageHashes.add(hash);
  return false;
}
```

3.生成唯一标识符

```js
原理​​：利用MD5将任意数据转为固定长度（32字符）的字符串，用作缓存Key或ID。

∙​​示例​​：
function generateID(data) {
  return md5(JSON.stringify(data)); // 对象转唯一ID
}
```

### 前端使用 md5 对文件生成唯一标识符

```js
import md5 from 'md5'
// 计算文件MD5的函数
const calculateFileMD5 = async (file: File): Promise<string> => {
  return new Promise((resolve, reject) => {
    const reader = new FileReader();
    reader.onload = e => {
      try {
        const arrayBuffer = e.target?.result as ArrayBuffer;
        const uint8Array = new Uint8Array(arrayBuffer);
        const hash = md5(uint8Array);
        resolve(hash);
      } catch (error) {
        reject(error);
      }
    };
    reader.onerror = () => reject(new Error('读取文件失败'));
    reader.readAsArrayBuffer(file);
  });
};
```

### MutationObserver

```js
const observer = new MutationObserver((mutation) => {
  mutation.forEach((mut) => console.log(mut))
})
observer.observe(target, {
  childList: true, // 监听子节点增删
  subtree: true, // 监听后代
  attributes: true, // 监听属性变化
  attributeOldValue: true,
})
```

### MutationObserver 特点

微任务执行：DOM 变更 → 微任务队列 → 回调
性能友好：批量 DOM 变化一次性处理，0 次回流

### 实战：无限滚动加载

```html
<div id="list"></div>
<div id="sentinel">↑ 触发加载 ↑</div>
<script>
  const observer = new MutationObserver(() => {
    const sentinel = document.getElementById("sentinel")
    if (sentinel && isInViewport(sentinel)) {
      loadMore()
    }
  })
  observer.observe(document.body, { childList: true, subtree: true })
</script>
```

### queueMicrotask

```js
window.queueMicrotask(() => {
  console.log("我在本轮微任务队列末尾执行")
})

// 实战：防抖里的微任务
function dobounce(fn, delay) {
  let timer
  return function (...arg) {
    clearTimeout(timer)
    timer = setTimeout(() => {
      queueMicrotask(() => fn.apply(this, agr))
    }, delay)
  }
}
```

#### queueMicrotask 特点

- 优先级：高于 setTimeout、低于 Promise.then
- 浏览器支持：Chrome 71+、Edge 79+、Safari 12.1+
- 用途：把非 Promise 逻辑塞进微任务队列，避免阻塞渲染

### 三、组合连招：微任务里监听 DOM

```js
queueMircotask(() => {
  new MutationObserver(() => {
    console.log("DOM changed in microtask")
  }).observer(document, {
    childList: true,
  })
})
```

> 执行顺序：DOM 变更 → MutationObserver → queueMicrotask → Promise.then → 渲染

### 两者总结

queueMicrotask：把任何逻辑塞进微任务队列末尾——快、轻、无 UI 阻塞
MutationObserver：DOM 变化后微任务触发——批量、0 回流、性能王者
