- fetch 中的 credentials: 'include'代表含义

::: info

- credentials: 'include' 始终在请求中携带凭据（包括跨域请求,如 Cookie、HTTP 认证信息等）,
- credentials: 'same-origin'​ 仅在请求的 URL 与调用脚本同源时携带凭据
- credentials: omit 绝不携带任何凭据,获取公开的、无需认证的静态资源

- 如果你在跨域请求中使用了 credentials: 'include'，仅仅配置客户端是不够的，服务器端必须进行相应的设置，否则请求会因为浏览器的同源策略而失败。服务器需要设置以下两个响应头：
- Access-Control-Allow-Credentials: true：这明确告知浏览器，服务器允许该跨域请求携带凭据。
- Access-Control-Allow-Origin 不能为通配符 _：此响应头必须明确指定为请求来源的确切域名（例如 https://www.example.com），而不能是通配符 _。这是因为出于安全考虑，当允许携带凭据时，通配符是被禁止的

默认行为：Fetch API 默认的 credentials 策略并非 'include'。根据规范，其默认值可能是 'same-origin'或 'omit'，但为避免混淆，最佳实践是始终根据你的需求显式设置该值。
注意 Cookie 的 SameSite 属性：即使你正确设置了 credentials: 'include'和服务器的 CORS 头，浏览器是否发送 Cookie 还会受到 **Cookie 自身 SameSite**属性的影响。例如，一个被标记为 **SameSite=Strict**的 Cookie 在跨站请求中将不会被发送

:::

- cookie 中的 SameSite 属性都有哪些，有啥含义

::: info

Cookie 的 SameSite 属性是一个重要的安全属性，用于控制 Cookie 在跨站请求中的发送行为，主要目的是防范 CSRF（跨站请求伪造）攻击。为了帮助你快速掌握其精髓，我先用一个表格总结它的三种模式，然后我们再深入聊聊一些关键细节。

- SameSite: Strict 最为严格：Cookie 仅在同站请求（即第一方上下文，当前页面 URL 与请求目标完全一致）中发送。任何跨站请求均不发送
- SameSite: Lax 适度宽松（现代浏览器的默认值）：允许部分安全的跨站请求（如通过链接跳转的 GET 请求）携带 Cookie，但会阻止非安全的跨站请求（如 POST 表单提交、AJAX 请求、iframe 加载等）携带 Cookie

- SameSite: 无限制：Cookie 可以在所有跨站和同站请求中发送。但必须与 Secure 属性一同设置，即只能通过 **HTTPS** 协议传输

:::

- 要求 SameSite=None 必须与 Secure 属性一同设置，主要是基于以下几点核心的安全考量

::: info

- 防止中间人窃听：跨站请求通常会穿越不同的网络边界，风险更高。Secure 属性确保 Cookie 只能通过加密的 HTTPS 连接传输。如果没有此要求，攻击者有可能在不安全的 HTTP 连接中窃取或篡改这些敏感的跨站 Cookie。
- 明确开发意图：这种强制配对要求开发者显式地声明其 Cookie 是需要跨站使用的。这并非浏览器多事，而是一种安全提醒，促使开发者慎重考虑是否真的需要开放跨站访问，避免因疏忽而留下安全漏洞。
- 浏览器策略的演进：这是现代浏览器（特别是 Chrome）安全模型的一次重要升级。在 Chrome 80 及之后的版本中，如果设置了 SameSite=None 却没有同时设置 Secure 属性，浏览器会直接拒绝这个 Cookie，视其为无效设置

:::

- cookie 中的 httponly 和 Secure 两者区别和意义

::: info

- httpOnly
  HttpOnly 属性的核心价值在于显著降低跨站脚本（XSS）攻击可能造成的损害。
  工作原理：当服务器设置 Cookie 时加上 HttpOnly 标志，现代浏览器会遵守此规定，使得客户端 JavaScript 脚本无法通过 **document.cookie**接口接触到这个 Cookie。但它并不影响浏览器在向同一域名发起请求时自动携带此 Cookie。
  重要提示：HttpOnly 只是一个属性标记，它本身没有值。正确的设置方式是 **Set-Cookie: session_id=abc123; HttpOnly**，而 HttpOnly=true 是错误的写法。

-局限性：需要明确的是，HttpOnly 并不能防止 XSS 攻击本身的发生，它只是极大地增加了攻击者通过 XSS 漏洞窃取用户会话 Cookie 的难度。因此，它应与严格的输入输出过滤等其他安全措施结合使用。

- secure
  Secure 属性的核心目标是确保 Cookie 仅在**加密通道**中传输，防止在网络传输过程中被窃听或篡改。
  工作原理：当一个 Cookie 被标记为 Secure 后，浏览器只会在通过 **HTTPS** 协议发起的请求中，才将其发送至服务器。如果请求使用的是不安全的 HTTP 协议，浏览器则不会发送此 Cookie。
  前提条件：要使 Secure 属性生效，你的网站必须全面启用 HTTPS。如果服务器没有正确配置 SSL/TLS 证书，该属性将无法提供有效的保护。

- 关键区别：Secure 属性仅保证传输过程的安全，但攻击者仍然可能通过其他非网络监听的方式（例如，如果用户计算机已感染恶意软件）获取到存储在本地的 Cookie 文件

- 为了最大限度地保护 Cookie 安全，最佳实践是同时为关键的 Cookie（尤其是会话标识符）设置 HttpOnly 和 Secure 属性
- 结合 SameSite 属性：现代浏览器还支持 SameSite 属性，用于控制 Cookie 在跨站请求中是否被发送。将 SameSite 设置为 Lax 或 Strict 可以有效防御跨站请求伪造（CSRF）攻击。**HttpOnly、Secure 和 SameSite**三者结合，能为 Cookie 提供非常全面的保护。
  :::

- Vscode 中的自动保存格式化配置:
  首先，确保 Cursor 的基础设置已正确开启代码格式化功能。
  开启保存时格式化：在 Cursor 的设置中搜索 editor.formatOnSave，确保其选项已被勾选。
  设置默认格式化器：在设置中搜索 editor.defaultFormatter，将其设置为 Prettier - Code formatter（对应的扩展 ID 通常是 esbenp.prettier-vscode）。这确保了在保存文件时，Prettier 会成为执行格式化的工具。
